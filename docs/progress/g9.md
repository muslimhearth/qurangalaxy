# G9: Semantic search with an Exact ↔ Meaning slider

## Done
- **Slider** "Exact ↔ Meaning" under the search field (`src/ui/SemanticSlider.tsx`), 0..1 in steps of 0.05, stored in `semanticWeight`. It has a label, works with the keyboard (arrows, Home, End) and touch, and has `aria-valuetext` ("Exact only", "40% meaning", "Meaning only").
- **Blend** (`src/search/blend.ts`): per root `score = w × semantic + (1 − w) × exact`. At weight 0 the result is the exact ranking, unchanged. Ties go to `rankMatches` (word count).
- **Runtime**:
  - `src/semantic/worker.ts` is a Web Worker. It loads the model when the slider first leaves 0 and embeds queries.
  - `protocol.ts` holds the messages and both ends: `createWorkerHandler` and `WorkerEmbedder`.
  - `useSemanticSearch` debounces queries (250 ms) and reports model download progress. Exact results stay usable during the load.
- **Search** (`verseIndex.ts`, `similarity.ts`, `aggregate.ts`):
  1. Compute the cosine of the query against the int8 verse matrix (6,236 × 384).
  2. Take the top 20 verses.
  3. Score each root as (sum of the similarities of its verses) × its inverse verse frequency, `log(N / verses) / log(N)`. Scale so the best root scores 1.
  4. Each match carries its 2 best verse keys.
- **Results**: a semantic result row shows the verse refs and a short English snippet of the best verse (two lines at most). Choosing a result still selects the root and sets `#/root/…`.
- **Build**:
  - `pnpm models` downloads the model at a pinned revision into `public/models/<id>/` (gitignored). `--all` downloads every candidate.
  - `pnpm embeddings` writes `public/data/embeddings.bin` (2.39 MB, 1.98 MB gzip) and `embeddings.json` (49 kB). Both are committed. The output is deterministic: two runs gave the same SHA-256.
- **Eval**: `pnpm eval:semantic [--model id] [--verbose]` runs the real models on 35 phrase queries (`scripts/semantic/eval-set.ts`). It caches verse embeddings in `data/raw/embeddings/`.
- **Tests**:
  - Unit tests for quantize, cosine top-k, verse→root aggregation (including the ubiquitous-root penalty), the index, the encoder, the blend, the worker protocol (fake embedder), the service, the hook, the slider, the snippet, the loader and the SearchBox meaning flow.
  - `e2e/semantic.spec.ts` (desktop + android): moves the slider (keyboard / touch), types "patience", expects صبر with verse refs, selects it, checks the hash, and asserts no third-party requests. It skips with a message when `public/models` is missing.

## Model eval (35 queries; hit = any expected root in the results)
Best setting per model, from a sweep over top-k verses and the inverse-frequency power:

| Model | Licence | q8 size | Verse build | Query (Node) | hit@1 | hit@5 | MRR |
|---|---|---|---|---|---|---|---|
| Xenova/all-MiniLM-L6-v2 (top 20) | Apache-2.0 | 23 MB | 102–136 s | 3 ms | 71% | **94%** | 0.81 |
| Xenova/gte-small (top 10) | MIT | 33 MB | 201 s | 2 ms | 80% | 91% | 0.85 |
| Xenova/bge-small-en-v1.5 (top 20, query prefix) | MIT | 33 MB | 212 s | 10 ms | 74% | 91% | 0.83 |

Top-k sweep for MiniLM (hit@1 / hit@5 / MRR): k10 66/89/0.76, k15 69/94/0.80, **k20 71/94/0.81**, k30 71/91/0.81.

**Choice: all-MiniLM-L6-v2, top 20 verses, power 1.** One query is 3% here, so the three models are within noise of each other. MiniLM is a third smaller, embeds faster and needs no query prefix.

Misses shared by all models:
- "pilgrimage": Saheeh says "Hajj", and the models do not link the two.
- "punishment for theft": the verse is out-ranked by general "punishment" verses.
- "the bee": only one verse names bees.

## Decisions
- **No third-party requests.**
  - The model is served from our own origin. In the browser, transformers.js runs in its "remote" mode with `remoteHost` set to `<origin><base>models/`. Its local-path mode fetched every file twice (a full GET just to read headers), so the model was downloaded twice (46 MB). Remote mode probes with a 1-byte Range request instead.
  - Node scripts use `allowRemoteModels = false` and read from disk.
  - The browser test checks that no request leaves localhost.
- **ONNX runtime self-hosted.** The worker imports `onnxruntime-web/ort-wasm-simd-threaded.{wasm,mjs}?url` and sets `wasmPaths`, so Vite emits them as hashed assets. A Vite alias maps `onnxruntime-web/webgpu` to `onnxruntime-web/wasm`. Without it the WebGPU build emits an unused 26 MB asyncify wasm. `onnxruntime-web` is a direct dependency, pinned to the version transformers.js 4.3.1 uses.
- **CSP**: transformers.js normally imports the runtime's JS from a `blob:` URL. The Caddy CSP (`script-src 'self' 'wasm-unsafe-eval'`) blocks that, so the browser sets `env.useWasmCache = false`. Checked: the production build works under the exact Caddy CSP header.
- **Dev server**: `optimizeDeps.include: ['@huggingface/transformers']`. Without it, Vite finds the dependency when the worker starts and reloads the page.
- **int8 with one global scale** (`EmbeddingsMeta.scale`). Rows are L2-normalized before quantization, so cosine = dot / scale. No renormalization is needed for ranking.
- **Ubiquitous roots**: the inverse verse frequency weight gives أله (1,879 verses) about 0.14 and صبر (93 verses) about 0.48. A root found in every verse scores 0. This is covered by tests.
- **Stale results**: semantic matches are shown only for the exact current query. While they load, the exact results show. If there are none, the list says "Searching by meaning…".
- The model load starts on the first slider move. The browser Cache Storage (`transformers-cache`) keeps the model for later visits.

## Sizes
- Initial UI chunk `index-*.js`: 245.8 kB (78.3 kB gzip, with G7 merged; G9 adds about 2 kB gzip). It contains no transformers.js or ONNX runtime code.
- Worker `worker-*.js`: 2.2 kB. It lazy-loads `transformers.web-*.js`: 500 kB (141 kB gzip).
- ONNX runtime: `ort-wasm-simd-threaded-*.wasm` 14.3 MB (3.7 MB gzip) + `.mjs` 24 kB.
- Model: `public/models/Xenova/all-MiniLM-L6-v2/` 23.7 MB (`model_quantized.onnx` 23 MB, `tokenizer.json` 0.7 MB).
- Data: `embeddings.bin` 2.39 MB (1.98 MB gzip) and `embeddings.json` 49 kB. They load only when meaning search is used.
- First meaning search on localhost: about 8 s (software, headless Chromium), then about 10 ms per query.

## Deploy
1. `pnpm install && pnpm models && pnpm build`. Vite copies `public/models/` into `dist/models/`. Without `pnpm models` the app works, and meaning search shows "Meaning search is unavailable". `scripts/ship.sh` (main) must run `pnpm models` before `pnpm build`; otherwise `rsync --delete` removes the model from the server.
2. The host should serve `.wasm` as `application/wasm` and support HTTP Range requests. Without Range, each model file costs about 0.2 MB extra per first load.
3. If the model changes: run `pnpm models` and `pnpm embeddings`, and commit the new `embeddings.*`.

## Open issues
- `e2e/app.spec.ts` "loads the real galaxy without errors" sometimes fails on a cold dev server: the canvas does not appear within 5 s. This also happens without G9 changes (1 of 3 runs).
- The ONNX runtime runs single-threaded: the page is not cross-origin isolated, so there is no SharedArrayBuffer. This is fast enough for one short query.
- `onnxruntime-web` is pinned to a dev build (`1.31.0-dev.20260914`) because transformers.js 4.3.1 depends on it. Update both together.
- `pnpm build` copies every model present in `public/models/`. Locally `--all` adds two unused candidates (66 MB) to `dist`. Deploy machines download only the chosen one.
